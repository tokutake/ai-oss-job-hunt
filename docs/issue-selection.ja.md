# 案件候補の評価基準

候補ごとに各項目を 0〜2 点で採点します。2 は明確に適切、1 は追加情報が必要、0 は不適合です。

[English](issue-selection.md)

| 観点 | 2 点の目安 |
| --- | --- |
| 受け入れ可能性 | Issue が open で外部貢献を受け付けており、必要なメンテナー合意がある |
| 重複の少なさ | 同じ変更を扱う open PR がなく、最近のマージにも修正が含まれていない |
| 小ささ | 一つの挙動・表示・ドキュメント変更に限定できる |
| 再現性 | 手順、環境、期待動作を確認できる |
| 変更の明確さ | 変更箇所と受け入れ条件が明確で、大きな設計判断を要しない |
| 検証可能性 | 既存コマンドや明確な手動確認で結果を確かめられる |
| 学習価値 | 関連技術とコードの流れをAIが説明できる |

**目安:** 10 点以上かつ「受け入れ可能性」「重複の少なさ」が各 2 点。0 点があれば理由を記録して保留または除外します。

## 保留・除外する条件

- 同じ問題を直す open PR がある、または既定ブランチに修正が入っている。
- Issue が closed / stale / abandoned、またはメンテナーが対応中と示している。
- 質問、広範な機能提案、初回貢献には大きすぎる設計変更。
- 再現できず、報告者やメンテナーの追加情報が必要。
- AIが確信を持って評価できない高影響のセキュリティ、課金、認証関連。
- ライセンス、CLA、貢献者ポリシーが不明。

## 調査チェックリスト

1. Issue の状態、本文、コメント、ラベル、最終更新日を読む。
2. Issue 番号、症状、関数名、ファイル名で open PR を検索する。
3. closed / merged PR に既存の修正がないか確認する。
4. 既定ブランチの最近の変更と該当コードを確認する。
5. 着手直前に再確認し、台帳に日付を記録する。

点数は候補比較の補助です。メンテナーの意向やリポジトリのルールを優先します。
